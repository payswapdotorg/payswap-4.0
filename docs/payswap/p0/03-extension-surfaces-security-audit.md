## 1. The extension surface map

### 1.1 Plugins

**What it is.** A manifest-driven extension format compatible with the Claude plugin layout. A plugin is a directory containing a manifest at `.zcode-plugin/plugin.json` (fallbacks: `.claude-plugin/plugin.json`, then `.codex-plugin/plugin.json` — `apps/zcode-cli/packages/adapters/src/plugins/index.ts`, constants `ZCODE_MANIFEST_PATH`/`CLAUDE_MANIFEST_PATH`/`CODEX_MANIFEST_PATH`). The manifest declares `commands`, `agents`, `skills`, `hooks`, `mcpServers`, `userConfig`, and `ui.surfaces` (type `PluginManifest` in `apps/zcode-cli/packages/contracts/src/plugins/index.ts`).

**Key symbols (exact).**
- `class NodePluginAdapter implements PluginPort` with `discoverPlugins` / `discoverPluginsSync` — `apps/zcode-cli/packages/adapters/src/plugins/index.ts:124`.
- `resolveCandidates` — four candidate sources, in order: inline dirs (`request.config.dirs`, `marketplace: "inline"`, `defaultEnabled: true`), bundled official roots (`ZCODE_OFFICIAL_PLUGIN_MARKETPLACE`), official cache scan (`scanOfficialCache`), and installed marketplace records (`listInstalledPluginRecords`, source `"cache"`).
- `loadPlugin` / `findManifest` / `readManifest` — manifest discovery and validation (`PLUGIN_NAME_PATTERN = /^[a-z0-9][a-z0-9._-]{0,127}$/`).
- `resolveEnabled(config, id, defaultEnabled)` — enablement resolves as `config.enabledPlugins[id] ?? defaultEnabled`; user config is authoritative (`apps/zcode-cli/packages/adapters/src/plugins/index.ts:994`).
- `resolveEnabledComponents` → `resolveSkillRoots`, `resolveCommandRoots`, `resolvePluginMcpServers` (see §1.2), `inspectPluginHooks`.
- `buildPluginReferenceCatalog(plugins)` — session-frozen identity catalog (`PluginReferenceCatalog`, `PluginReferenceCatalogEntry` with `skillQualifiedNames` (`name:skill`), `subagentNames` (`name:agent`), `mcpServerNames`, `uiSurfaces`) — `apps/zcode-cli/packages/core/src/plugin-reference/catalog.ts`. Built once at session runtime creation; not hot-reloaded.

**Lifecycle & state owner.** The **zcode-cli process owns plugin truth**: it reads/writes the `~/.zcode` plugin storage root and resolves the runtime. The Desktop/Web host has no second copy — `packages/services/src/plugins/pluginManagementService.ts` states this explicitly in its header comment ("The source of truth for plugin installation/marketplaces/enable-disable is in the zcode-cli process (reads/writes the ~/.zcode plugin directory and hot-updates the runtime state); the host holds no copy") and is a thin telemetry-wrapping proxy over `IZCodeAgentService` agent-protocol methods (`installPlugin`, `uninstallPlugin`, `setPluginEnabled`, `configurePlugin`, `restoreBuiltinPlugin`, …). The legacy host-side `IPluginsService` is retired: `packages/services/src/plugins/pluginsService.ts` throws `"Legacy plugin management has been retired in ZCode Agent mode"` and returns `capability: { supported: false }`.

**Install/enable persistence.**
- Enable/disable + options: `setZCodePluginEnabled` / `configureZCodePlugin` / `uninstallZCodeMarketplacePlugin` in `apps/zcode-cli/packages/bootstrap/src/plugins.ts`, writing through `@zcode/adapters/config` (`updatePluginEnabledInFileConfig`, `updatePluginOptionsInFileConfig`, `removeSuppressedBuiltinInFileConfig` — `apps/zcode-cli/packages/adapters/src/config/file-config.adapter.ts`).
- Install: `installMarketplacePlugin` / `uninstallMarketplacePlugin` — `apps/zcode-cli/packages/adapters/src/plugins/marketplace.ts:790/851`. Dependency closure via `resolveDependencyClosure` (cross-marketplace deps only when allowed by `allowCrossMarketplaceDependenciesOn`), atomic directory activation (`apps/zcode-cli/packages/adapters/src/plugins/atomic-directory.ts`), storage lock `withPluginStorageLock` (`apps/zcode-cli/packages/bootstrap/src/lib/plugin-storage-lock.ts`).
- Package integrity: official CDN zips are sha256-verified — `apps/zcode-cli/packages/adapters/src/plugins/zip-source.ts` (`ZIP_REQUIRED_SHA256_PATTERN`, "Plugin zip sha256 mismatch: expected=…, actual=…" at line ~109; `readRequiredZipPluginSourceSha256` in `marketplace.ts:1530`). Git/GitHub/URL/directory/npm personal sources have **no signature gate** by design (personal sources are user-added trust).
- Plugin data directory: `getPluginDataDir(storageRoot, pluginId)` = `<storageRoot>/data/<sanitizePluginId(pluginId)>` (`marketplace.ts:2866`), exposed to the plugin as `${ZCODE_PLUGIN_DATA}`.
- Builtin uninstall is a marker, not deletion: user-config `suppressedBuiltins`; restore via `restoreBuiltinPlugin` (matches `CONTEXT.md` "Restorable Builtin").

**Registration into the session.** `listZCodePlugins` (`apps/zcode-cli/packages/bootstrap/src/plugins.ts`) → tool roots, skill roots, hooks, and namespaced MCP servers merged into the runtime; protocol surface for the host: `apps/zcode-cli/packages/bootstrap/src/zcode-protocol/plugins.ts` (methods `zcodePlugins/Install`, `/SetEnabled`, `/Configure`, `/RestoreBuiltin`, `/Overview`, … schemas in `@zcode/shared`). In-session mutations go through the facade `createPluginFacadeForApp` (`apps/zcode-cli/packages/bootstrap/src/app/plugin-facade.ts`) which mirrors `enabledPlugins`/`suppressedBuiltins` locally.

**Callers.** Store UI: `packages/ui/src/settings/PluginStorePage.tsx`, `PluginStoreListView.tsx`, `InstalledPluginManagement.tsx`, etc. (domain vocabulary: `CONTEXT.md`, verified against `recommendedPlugins.json` in that directory). Host service: `packages/services/src/plugins/pluginManagementService.ts`. Data sync of inline plugins: `packages/services/src/plugin-sync/pluginSync.ts` + `packages/services/src/data-sync/inlinePluginDataSync.ts`.

**Store UI terminology check (CONTEXT.md vs source).** Verified: `publisherType` (`official`/`community`) appears in `pluginManagementService.ts` telemetry (`installed.listing.publisherType`); `ui.surfaces` gating and `componentTypes` come from the marketplace/catalog code (`parseEntryStoreListing`, `enumeratePluginComponents` in `apps/zcode-cli/packages/adapters/src/plugins/`). No discrepancy found.

### 1.2 MCP (adapters + tool runtime)

**Two layers.**

(a) **Adapter layer (connection)** — `apps/zcode-cli/packages/adapters/src/mcp/index.ts` (2563 lines):
- `createMcpAdapter(options)` → `class NodeMcpAdapter implements McpPort`; `createMcpAdapterConnectionPool` for shared leases.
- Transports: `stdio` (`StdioClientTransport` from `@modelcontextprotocol/client/stdio`), `http` (`StreamableHTTPClientTransport`), `sse` (`SSEClientTransport`).
- stdio env hygiene: `buildMcpStdioEnv` (`apps/zcode-cli/packages/adapters/src/mcp/network.ts`) = `applyNetworkEgressEnv(sanitizeZCodeRuntimeEnv(filterStringEnv(env)), …)` — see §4.2 for what is stripped.
- HTTP egress: `createMcpTransportFetch` (proxy/CA-aware, `withoutNetworkCapture`).
- OAuth: `apps/zcode-cli/packages/adapters/src/mcp/oauth*.ts` (`loadCredentialPair`, `oauth-lease.ts`, `runMcpInteractiveAuthorization`); credentials land in the shared credential store (`createSharedZCodeCredentialStore` from `../auth/shared-credentials.js`).
- Official auth: `parseZCodeOfficialAuth` + `buildOfficialProvenance` (`apps/zcode-cli/packages/adapters/src/plugins/mcp-official-auth.ts`) — the host generates `official` provenance; a manifest cannot forge it (see §4.4).

(b) **Tool runtime (model-facing)** — `apps/zcode-cli/packages/core/src/mcp/index.ts`:
- `registerMcpTools(registry, mcpPort, descriptors, options)` projects MCP tool descriptors into the core `ToolRegistry` as `mcp__<normalized-server>__<tool>` (`toMcpToolName`, `toModelVisibleMcpNamePart` in `name.ts`). Plugin servers are namespaced at config-resolution time as `plugin:<plugin-name>:<server>` (`toNamespacedServerName` in `apps/zcode-cli/packages/adapters/src/plugins/mcp.ts:67`), so model-visible names are e.g. `mcp__plugin_zcode-cua_computer-use__<tool>` (confirmed in `apps/zcode-cli/packages/core/tests/mcp-tool-bridge.test.ts`).
- `createMcpToolEntry(name, descriptor, mcpPort, officialCuaAuthorityVerified, …)` — permission metadata for every regular MCP tool: `needsApproval = true`, `riskLevel` low (readOnlyHint) / medium / high (destructiveHint), `sideEffectScope: "network"` (except host `node_repl` `js` tool → `"system"` + high risk), `permission: { permission: "mcp", patternSources: ["toolName","input","network"], denyPriority: "beforeAsk" }`, default timeout `MCP_TOOL_TIMEOUT_MS = 30_000`, result budget 100 KiB inline / 50 KiB model (official CUA gets 256 KiB).
- `RegisterMcpToolsOptions.officialCuaServerNames` — "verified by the runtime with unforgifiable product authority credentials … when omitted, fail-closed; all MCP are treated as ordinary tools". The official CUA model-name projection (`mcp__computer-use__*`) is gated on this; third-party lookalike servers cannot obtain it (test `mcp-tool-bridge.test.ts:117` "trusted vs lookalike").
- **App-provided tools** (page → model direction): `createMcpAppProvidedToolEntry` (`apps/zcode-cli/packages/core/src/mcp/app-tools.ts`) — model name `app__<server>__<tool>`, execution delegated to the hosting sandbox page via the bootstrap instance mailbox; "read-only auto-allowed, the rest go through the existing approval; the page is untrusted sandboxed code, risk is at least medium"; `askOptions: { allowAlways: "session" }` — "always allow" for app tools is session-scoped and never persisted.
- Workspace (project `.mcp.json`) MCP servers are additionally gated by the **workspace MCP trust store**: `apps/zcode-cli/packages/bootstrap/src/workspace-mcp-trust/index.ts` (`STORE_NAME = "workspace-mcp-trust-v1.json"`, `declarationDigest` sha256-bound records; "unknown, stale, or corrupted records are denied by default"). Plugin and user-level MCP are out of that module's scope (they are covered by the plugin install action / user config respectively).

**State owner.** The CLI runtime owns connections, tool registration, and permission semantics; the Desktop host only renders status and relays calls (`packages/services/src/runtime-tools/`, `packages/services/src/mcp-sync/` for settings surfaces — not audited in depth here).

### 1.3 UI Plugins / MCP Apps

**What it is.** Interactive HTML pages served by a plugin's MCP server as `text/html;profile=mcp-app` resources (`ui://…` URIs), rendered inside an Electron **webview sandbox** in the Desktop renderer. Spec constants and wire types: `packages/shared/src/mcp-apps/` (`CONTRACT.md`, `contract.ts`, `hostContract.ts`, `appTools.ts`, `sampling.ts`, `resourceMime.ts`, `toolMeta.ts`).

**Declaration.** Manifest `ui.surfaces[]` parsed by `parsePluginUiSurfaces` (`apps/zcode-cli/packages/adapters/src/plugins/ui-surfaces.ts`): each surface requires `id` (charset `^[A-Za-z0-9][A-Za-z0-9_.-]*$`, ≤128), `title` (string or locale map), `server` (must name a server declared in `mcpServers`; runtime name is rewritten to `plugin:<name>:<server>`), `resourceUri` (must start with `MCP_APPS_UI_RESOURCE_SCHEME` = `ui://`, ≤2048 chars), `availability: "session"` (only supported value). Tools opt into UI by `_meta.ui.resourceUri` + `_meta.ui.surface`; `_meta.ui.visibility` controls model-vs-app-only visibility (`resolveMcpToolVisibility`; tools without `"model"` in visibility stay out of provider contracts but remain callable via UI callback — `apps/zcode-cli/packages/core/src/mcp/index.ts:131-134`).

**Mounting chain (Desktop, local workspaces only).**
1. Tool result or Side Pane entry requests a page → `packages/ui/src/plugin-ui/app/pluginUiPageManager.ts` / `pluginUiSurfaceStore.ts` (UI layer).
2. `IPluginUiBridgeService` (`packages/services/src/plugin-ui-bridge/contract.ts`, impl `pluginUiBridgeService.ts`): `prepareSandbox` obtains a source-bound runtime credential (`runtimeId`/`token`/`generation`/`resourceUri`) from the Agent, reads the HTML resource (limit `MCP_APPS_HTML_MAX_BYTES` = 16 MiB; MIME must be `text/html;profile=mcp-app` or `text/html`), and registers with Main. "HTML goes via Host to Main; the Renderer only obtains a handle" — the renderer never receives raw HTML or connection config.
3. Main-process sandbox host: `installPluginSandboxHost` (`packages/desktop/src/main/pluginSandbox/host.ts`), registry `createPluginSandboxRegistry` (`registry.ts`, cap 64 live instances, pin/unpin, `markUserGesture` 5-second one-time gesture token), protocol handler (`protocol.ts`, custom `zcode-sandbox://` scheme), session partition prep (`session.ts`).
4. The renderer embeds a `<webview>` whose src is the shell URL `zcode-sandbox://shell-<sandboxId>/…`; `configurePluginSandboxGuest` / `attachPluginSandboxGuest` (`packages/desktop/src/main/pluginSandbox/guestPolicy.ts`) harden the guest and wire a single `MessageChannelMain` (`InternalChannels.PluginSandboxPorts` to the host renderer, `PluginSandboxChannels.Init` + port1 to the guest preload `packages/desktop/src/preload/pluginSandbox/hostBridge.ts` → renderer relay `packages/desktop/src/renderer/src/plugin-sandbox/relay.ts`).
5. Page-side SDK is the official `@modelcontextprotocol/ext-apps` (pinned 2.0.0 per `UI_PLUGIN.en.md`); a legacy `window.zcode` **alias API exists inside sandbox pages only** (`packages/desktop/src/renderer/src/plugin-sandbox/alias.ts`, `aliasApi.ts`, `openaiAlias.ts`) — this is distinct from the main-app preload bridge (§5). The sandbox shell/alias/instance resources are all `Cache-Control: no-store` (`pluginSandbox/CONTRACT.md` "instance resource cache boundary", consistent with `protocol.ts`).

**State owners.** Agent owns instance credentials, call attribution, permission, cancellation and terminal states; Host bridge owns prepare/read/close plumbing; Main owns guests, ports, partitions, and browser permissions; renderer page plane (`packages/ui/src/plugin-ui/adapters/pluginUiPagePlane.ts`) owns layout/anchors and live-page moves. `widgetState` is renderer-memory only (never persisted; `pluginUiWidgetStateStore.ts`, `packages/ui/src/plugin-ui/CONTRACT.md`).

**Gen UI** reuses the sandbox registration payload with `contentKind: "gen-ui"`, separate in-memory partition `gen-ui-<appIdentity>`, no pluginId/serverName, and no native permissions (`packages/desktop/src/main/pluginSandbox/CONTRACT.md` §Gen UI; `genUi.ts` in renderer plugin-sandbox; domain `packages/shared/src/gen-ui/`).

### 1.4 Skills

- CLI adapter: `class NodeSkillAdapter implements SkillPort` — `apps/zcode-cli/packages/adapters/src/skills/index.ts` (`discoverSkills`, `parseSkill` with `SAFE_FRONTMATTER_KEYS = {name, description, when_to_use, license, metadata}`, `DEFAULT_MAX_SKILL_BYTES = 100_000`). Roots resolved by `resolveDefaultSkillRoots` (`roots.ts`): workspace `.zcode/skills` (with `.agents/skills` fallback), user `~/.zcode/skills` (with `~/.agents/skills` fallback), plus plugin-provided `SkillRoot`s (`source: "plugin"`, `followSymbolicLinks: false` for plugin roots — symlink escape refused).
- Host-side service: `packages/services/src/skills/skillsService.ts` (same root conventions, `_meta.json` metadata, `~/.zcode/cli/config.json` skill enable overrides; header comment "aligned with apps/zcode-cli/packages/adapters/src/skills/index.ts:19").
- Skills are prompt-layer extensions: a `SKILL.md` frontmatter `name`/`description` is surfaced to the model; the skill body is read on demand. **A skill has no code execution surface of its own** — any side effects happen through the tools the model already has (Bash, MCP, …) and are subject to the normal permission flow.
- Plugin skills appear as `<plugin-name>:<skill-name>` qualified names via `PluginReferenceCatalogEntry.skillQualifiedNames`.
- Repository-process skills: `.agents/skills/*` at repo root (e.g. `architecture-governance`, `feature-boundary-planner`, `electron`, `react-best-practices`, …). These are developer/agent workflow skills (markdown), loaded the same way as any user skill from `~/.agents`-style roots; they are not a runtime extension mechanism for end-user code.

### 1.5 Hooks

- Runner: `createConfiguredHookRunner` + `class InMemoryHookRunner` — `apps/zcode-cli/packages/core/src/hooks/configured-runner.ts`, `runner.ts`. Hook sources: user/global config events, plugin hooks (`hook.plugin` context attached by `attachPluginToHook` with `HookPluginContext { id, name, rootPath, dataPath }`), and workspace hooks.
- Execution: `createConfiguredHookCallback` (`configured-runner-callback.ts`) — `hook.type === "command"` runs a **shell command** via `options.executionPort.run({ command: { mode: "shell", command: expandPluginVariables(hook.command, hook.plugin, …), shell: hook.shell }, env: createPluginEnvOverlay(hook.plugin, …), … })`; `hook.type === "process"` spawns a process. Hooks receive tool input on stdin (`createCompatibleHookStdin`), can add context, and — for `PermissionRequest` and `PreToolUse` events — can participate in approval decisions (raced with the human responder via `racePermissionResponders`, `apps/zcode-cli/packages/core/src/tool/executor/permission-request.ts`). A tool's `alwaysAsk` declaration is a structured "confirmation that cannot be erased" marker (`PermissionDecisionResult.alwaysAsk`) that hooks cannot silently remove (`permission/service.ts:79-83`).
- **Workspace hook trust**: project config hooks are stripped from the executable patch at load time and parked in a candidate side-channel (`apps/zcode-cli/packages/adapters/src/config/project-config.adapter.ts` `normalizeProjectConfig` — "Project Hook declarations are retained only in the immutable candidate side-channel", diagnostic `config_project_hooks_pending_trust`). Runtime admission: `class WorkspaceHookRuntimeAdmission` (`apps/zcode-cli/packages/core/src/hooks/workspace-hook-runtime-admission.ts`) + trust evaluation (`workspace-hook-trust-evaluation.ts` — states `trusted_persistent`, `blocked_policy`, `blocked_untrusted`, `revoked`, `stale_digest`, `pending_trust`), policy (`workspace-hook-policy.ts`, `DEFAULT_POLICY = { mode: "user_decides", … }`, alternative `allow_trusted_only`), records store (`workspace-hook-trust-records.ts`). Digest-bound, fail-closed.
- **Plugin hooks are NOT behind that trust gate**: `canRunPluginHooks(_loaded) { return true; }` with the source comment "we have abandoned the trust boundary of 'only official can execute hooks'; third-party plugin hooks will execute directly" (`apps/zcode-cli/packages/adapters/src/plugins/index.ts:371-376`). Installing a third-party plugin that declares hooks is, today, sufficient for its shell commands to run on hook events (subject only to the install/enable action).

## 2. The sandbox and isolation contract

**What sandboxes exist.**
1. **Plugin/MCP-App webview sandbox** (the one that matters for UI Plugins) — Electron `<webview>` guest, custom `zcode-sandbox://` protocol, per-server persistent partition. Files: `packages/desktop/src/main/pluginSandbox/*` (contract `contract.ts` + `CONTRACT.md`, `host.ts`, `registry.ts`, `protocol.ts`, `session.ts`, `guestPolicy.ts`, `csp.ts`, `permissions.ts`, `permissionGate.ts`, `capture.ts`, `genUiVendor.ts`), preload `packages/desktop/src/preload/pluginSandbox/`, renderer `packages/desktop/src/renderer/src/plugin-sandbox/`.
2. **node_repl host worker** (`apps/zcode-cli/packages/node-repl-host/`) — out of this audit's depth; noted as a separate code-execution surface (its `js` tool is classified `sideEffectScope: "system"`, risk `high` in `createMcpToolEntry`).
3. **MCP stdio server processes** — plain child processes, isolated only by env hygiene + user-level OS privileges (no OS sandbox found for them; see §6).

**The boundary (plugin webview), enforced where.**
- Guest webPreferences forced by `configurePluginSandboxGuest` (`guestPolicy.ts:24-59`): `contextIsolation: true`, `sandbox: true`, `webSecurity: true`, `nodeIntegration: false`, `nodeIntegrationInSubFrames: false`, `webviewTag: false`, `plugins: false`, `disableDialogs: true`, `allowRunningInsecureContent: false`; caller-supplied `params.preload/nodeintegration/…/webpreferences` are deleted. `will-attach-webview` additionally requires sandboxId + partition + `ownerWebContentsId` triple match (reject reasons `not-shell-url | unknown-sandbox | partition-mismatch | owner-mismatch`).
- Origins: shell `zcode-sandbox://shell-<id>/`, plugin frame `zcode-sandbox://plugin-<appIdentity>`; navigation allow-list is exactly these two origins (`isAllowedNavigation` in `guestPolicy.ts`); popups denied (`setWindowOpenHandler(() => ({ action: "deny" }))`); reload/cross-document navigation of the shell or the plugin frame revokes the registration and invalidates ports/authorizations (`did-start-navigation` handling); `frame-ancestors` pinned to the stable shell origin.
- Partition: `persist:plugin-sandbox-v2-<hash(appIdentity)>` — derived from trusted app identity (server identity), so storage is per-server and survives restarts; sandboxId is per-Electron-lifetime and random `[A-Za-z0-9-]` (CSP host-safe, `PLUGIN_SANDBOX_CSP_HOST_SAFE_ID`).
- CSP (`csp.ts`): plugin document `default-src 'none'; script-src 'self' 'unsafe-inline' blob: data: [relaxations] [declared resourceDomains]; …; connect-src <declared or 'none'>; frame-src <declared or 'none'>; form-action 'none'; frame-ancestors <shellOrigin>`; `'unsafe-eval'`/`'wasm-unsafe-eval'` only when resource `_meta["zcode/csp"]` declares them. Shell CSP is stricter (`script-src 'self'`, `connect-src 'none'`) — the trusted shell loads only packaged assets. All instance protocol responses are `Cache-Control: no-store`.
- Permissions-Policy (`buildPluginSandboxPermissionsPolicy`): undeclared features `()`; notably **`payment=()`, `usb=()`, `display-capture=()`, `clipboard-read=()` are always disabled** — in-page Web Payment APIs are categorically off for plugin pages.
- Native permissions (camera/microphone/geolocation/clipboardWrite): four-key model `McpAppsResourcePermission`; undeclared → deny; camera/mic/geo additionally prompt once per partition per run (in-memory consent only — `createPluginSandboxPermissionGate` `consented` Map; "valid for the duration of this run; it will be asked again after restarting the desktop app"); `clipboardWrite` allowed by declaration. Requests are bound to the actual guest/record/initId and re-validated after async confirmations ("a confirmation on an expired page must not authorize a replacement page").
- Comms: exactly one MessageChannel per instance (`PLUGIN_SANDBOX_PORT_NAME` per `packages/shared/src/mcp-apps/CONTRACT.md`); the shell only forwards raw JSON-RPC. Page → server calls go through the Agent (`mcp/uiCallTool`-family with instance credentials checked by the Agent); page-initiated `resources/read` is capped at `MCP_APPS_UI_READ_RESOURCE_MAX_BYTES` (8 MiB) with a MIME allow-list (`MCP_APPS_UI_READ_RESOURCE_MIME_ALLOWLIST`), enforced agent-side.
- Capacity/lifecycle: max 64 registrations; pinned live instances are not evicted; dispose = close ports, then Main navigates the guest to `about:blank` once, then close. `setExecutionActive` only accepts host sender MCP requests for the current sandboxId/initId.

**Threat model (as evidenced by code comments and checks).** The page is untrusted ("the page is untrusted sandboxed code" — `core/src/mcp/app-tools.ts`); defense rests on: origin/partition separation, CSP default-deny with declared domains, no Node, no popups, no payment/USB, single audited port, instance-credential-bound IPC, host-side permission gate with declared+consented sets, and revocation-on-navigation. Main holds no MCP permission policy and no business state ("Main does not execute MCP permission policy, does not save sessions, queues, widgetState" — `pluginSandbox/CONTRACT.md`).

**The confused-deputy threat is explicitly modeled for process-level credentials**: `packages/shared/src/runtimeEnv.ts` strips `ZCODE_CUA_PERMISSION_BROKER_SOCKET`, `ZCODE_CUA_PERMISSION_BROKER_TOKEN`, `ZCODE_CUA_PLUGIN_AUTHORITY`, `ZCODE_OFFICIAL_ENDPOINT(_TOKEN)`, OTEL/telemetry secrets, and remote proxy material from **all** subprocess environments (`SANITIZED_RUNTIME_ENV_KEYS`, `sanitizeZCodeRuntimeEnv`), with the rationale in source: "otherwise a malicious MCP within the same agent, or a command triggered by prompt-injection, could directly drive the authorized Helper (confused-deputy)". Targeted re-injection happens only via dedicated paths (`getCapturedZCodeCuaBrokerCredentials`), never via inherited env.

## 3. The permission model

**Where enforcement lives.** The **CLI runtime is the enforcement point** for tool calls. `class PermissionService` (`apps/zcode-cli/packages/core/src/permission/service.ts`) computes a `PermissionDecisionResult` (`decision: "allow" | "ask" | "deny"`, `ruleId`, `escalated`, …). The executor's flow (`apps/zcode-cli/packages/core/src/tool/executor/`): `permission-flow.ts` → `requestPermissionResponse` (`permission-request.ts`) races two responders — the **human/UI broker** (`deps.permissionBroker.requestPermission` → published as a session event/interaction handled by Desktop/Web/TUI clients) and **`PermissionRequest` hooks** — via `racePermissionResponders`. Responses are validated (`permission-responder-race.ts`, `permission-response.ts`); suggested rule updates from the user's choice are persisted by `persistProjectPermissionUpdates` (`permission-rules-persistence.ts`) into the session store (project-scope rules) or session ruleset; session-scoped "always allow" lives in `PermissionService.sessionRules` (memory; one instance = one session).

**Declaration.** Tools declare a `permission: ToolPermissionSpec` (`permission: "mcp"`, `riskLevel`, `sideEffectScope`, `needsApproval`, `patternSources`, `denyPriority`, `askOptions`) plus metadata (`readOnly`, `destructive`, `concurrentSafe`). For MCP tools the spec is synthesized in `createMcpToolEntry` / `createMcpAppProvidedToolEntry` (§1.2). Capability-derived fields are resolved in `resolveCapability`/`permission-capability.ts`.

**Decision order (verified in `checkPermission`).** plan-mode transition gate → `requiresUserInteraction` (deny if `disallowedTools`) → guarded dangerous-command single-use ask → `alwaysAsk` gate (`checkAlwaysAsk`: auto-mode deny, `disallowedTools` deny, project deny, session allow, owned-workflow-amend allow, else ask — ask **survives yolo**) → **yolo/guarded allow** (`ruleId: "mode.yolo"`, "Yolo mode bypasses permission prompts") → auto-mode deny → `disallowedTools` deny → project deny → project ask → special pre-approvals (`ReplyToChannel`, `CronPauseSelf`, workflow-draft writes, preapproved WebFetch) → project allow → `allowedTools` allow → edit-mode → build-mode defaults.

**Rules.** `PermissionRuleset` with `allow`/`ask`/`deny` arrays of `PermissionRuleValue` (`toolName` + `ruleContent` wildcard/prefix patterns over subjects like `command`, `url`, `file_path`; `rule-matching.ts`, `webFetchRuleSubjects`). Persistence: project rules in the session store (SQLite via `sessionStore.getProjectPermission`/`updateSession`); per-session grants in memory.

**Identities/roles that exist.** No user-role RBAC. Identity axes are: collaboration `mode` (`build`/`edit`/`plan`/`guarded`/`yolo`/`auto`), tool capability metadata, `PermissionCapabilityGroup` (e.g. `PermissionCapabilityGroup.OfficialCua`), workspace identity (`workspaceIdentity` for isolation), plugin identity (`plugin:<name>@<marketplace>`), sandbox instance credentials (`runtimeId`/`token`/`generation`), and sandbox partition (per server). "Full access" is an explicit, receipt-tracked grant: `grantPermissionFullAccess` (`apps/zcode-cli/packages/core/src/runtime/permission-full-access.ts`) with idempotent receipts and pending-grant recovery (`permission-grant-recovery.ts`).

**Browser-permission layer (sandbox pages)** is separate and additive (§2): declared-in-`_meta.ui.permissions` + in-memory per-partition consent.

**The "model cannot self-authorize" precedents (all verified in source).**
1. Every regular MCP tool is `needsApproval = true` regardless of the server's claims (`createMcpToolEntry`, `core/src/mcp/index.ts:148`); only the human broker, session rules the human created, or explicit project rules can allow.
2. Trusted capability groups are **not name-granted**: `matchesRuleScope` honors the `official_cua` rule key only when the tool entry carries a host-verified `permissionCapabilityGroup === PermissionCapabilityGroup.OfficialCua` — "server/tool names can be spoofed by a third party, therefore this permission must never be expressed with name wildcards" (`permission/service.ts:335-347`); `RegisterMcpToolsOptions.officialCuaServerNames` is "verified by the runtime with unforgifiable product authority credentials … when omitted, fail-closed".
3. App tools' "always allow" is session-only and never written to persistent rules (`askOptions: { allowAlways: "session" }`, `core/src/mcp/app-tools.ts:101-102`).
4. Sandbox native permissions require declaration + human consent; consent is in-memory per run and bound to the live instance ("a confirmation on an expired page must not authorize a replacement page").
5. `alwaysAsk` is a structured marker that hooks cannot erase ("confirmation that cannot be erased", `PermissionDecisionResult.alwaysAsk`).
6. Automations cannot mutate their own schedules (`AUTOMATION_MUTATION_TOOL_NAMES` denylist), and owned-amend allowances are keyed to run ownership, not to fields the model could fabricate.

## 4. Security invariants PaySwap provider plugins must satisfy

### 4.1 Credential handling — where secrets may and may not flow

Existing secret/credential utilities:
- **`ICredentialService`** (`packages/services/src/credential/credential.ts`: `load`/`save`/`delete` by key) — host-process service; storage `credentials.json` in the app config dir; values encrypted AES-256-GCM (`enc:v1:` prefix) by `createCredentialCipherProvider` (`providers/credentialCipherProvider.ts`). **Gap:** the key is `sha256(ZCODE_CREDENTIAL_SECRET env)` or, absent that env, the deterministic fallback `zcode-credential-fallback:<platform>:<homedir>:<username>` — i.e. obfuscation, not OS-keychain protection. The file's own comment plans an Electron `safeStorage` migration that is **not implemented** ("the host process will need to request encrypt/decrypt from the main process"). Renderer access is via RPC only ("the consuming side (renderer) only calls via RPC and is unaware of the storage location"); preload bridge comment confirms credentials no longer traverse `window.zcode` (`packages/desktop/src/preload/index.ts:260-264`).
- **Plugin `userConfig`** is the native plugin configuration surface: `PluginUserConfigOption { type, required, sensitive?: boolean, … }` (`apps/zcode-cli/packages/contracts/src/plugins/index.ts:56-64`). `sensitive: true` restricts **template expansion**: `resolveTemplate` throws `PluginVariableError` ("Sensitive plugin user_config value cannot be used in this field") unless the sink is `allowSensitive` — only `env` records, `headers`, and oauth `clientSecret` (`apps/zcode-cli/packages/adapters/src/plugins/mcp.ts:388-449`). Non-sensitive sinks (command, args, cwd, url) can never receive sensitive values or arbitrary env-var expansions. **But storage is plaintext:** `configureZCodePlugin` → `updatePluginOptionsInFileConfig` → `atomicWriteJson` into the scoped config file (`apps/zcode-cli/packages/adapters/src/config/file-config.adapter.ts:299-315`); workspace scope is `<workspace>/.zcode/config.json` (`apps/zcode-cli/packages/bootstrap/src/plugins.ts:1312-1315`). A PaySwap plugin's `userConfig`-entered secret key would sit in plaintext JSON — **invariant: provider secrets must NOT be designed to live in `userConfig` for anything stronger than convenience; the durable answer is a new credential path modeled on `ICredentialService` (or extending it), with targeted injection at server-spawn time.**
- **Env hygiene precedent (the model to follow):** `sanitizeZCodeRuntimeEnv` strips all host/session credentials from every subprocess env, and sensitive material reaches only its designated consumer via targeted injection (CUA broker socket → only the official zcode-cua server's env; official endpoint token → per-session injection). A PaySwap provider secret must follow the same rule: inject **only** into the provider's own MCP server process env at `resolvePluginMcpServers`/transport spawn time, never into agent-global env, Bash env, hook env, or logs (`AGENTS.md` log rules: "never write credentials … into logs, examples, or commits").
- **Identity injection is host-authoritative:** `env[ZCODE_PLUGIN_ID_ENV_KEY]` ("ZCODE_PLUGIN_ID") is written by the resolver **after** the manifest env spread so a manifest cannot forge another plugin's identity (`apps/zcode-cli/packages/adapters/src/plugins/mcp.ts:232-235`); official auth `provenance` is host-generated and overwrites any manifest attempt (§1.2).
- **Sandbox pages never see tokens:** `plugin-ui-bridge` "the host reads provider/profile.id from the trusted account repository and hashes it into accountContext, without passing the token" (`packages/services/src/plugin-ui-bridge/CONTRACT.md`, verified by `instanceAccounts.ts` usage in the module) — pages get instance-scoped runtime credentials, not provider secrets.

### 4.2 IPC/process boundaries

- Desktop ↔ Agent is stdio ZCode Protocol; protocol changes must go through `packages/shared/src/zcode-protocol/index.ts` with strict types + runtime validation (`AGENTS.md` "Processes, protocols and remote control"). PaySwap must not invent side channels.
- Main process "handles windows, native operations, process scheduling and message forwarding, and does not carry task/session business state" (`AGENTS.md`); plugin sandbox Main layer "does not execute MCP permission policy, does not save sessions, queues, widgetState" (`pluginSandbox/CONTRACT.md`). Provider business state belongs in the provider's MCP server process + plugin data dir, not in Main or the renderer.
- The only sanctioned renderer→host data path for plugin pages is the single sandbox MessageChannel running JSON-RPC; `resources/read` from pages is size-capped (8 MiB) and MIME-allow-listed, agent-enforced.

### 4.3 Sandbox escape rules (for any PaySwap UI)

- No Node, no popups, no new windows, no payment/USB APIs; navigation locked to the two sandbox origins; CSP `default-src 'none'` with only declared domains for `connect-src`/`frame-src`/resources; `form-action 'none'`.
- Provider pages must not attempt `file://`, native bridges, or expecting `window.zcode` main-app bridge — the sandbox `window.zcode` alias is a page-compatibility shim, not the preload bridge.
- Declared native permissions only (camera/mic/geo/clipboardWrite); consent is per-run and re-asked after restart.

### 4.4 Permission scoping

- PaySwap provider tools ride `permission: "mcp"` with `needsApproval: true` by default. Financial mutations (charges, refunds, payouts) should be modeled as `destructiveHint: true` (→ risk `high`) — but note the hints are **server-asserted**: a hostile server can lie about `readOnlyHint`. The runtime does not independently verify MCP annotations. Treat annotations as advisory; rely on the human approval flow (and consider asking upstream for an `alwaysAsk`-style hard-confirm path for money-moving tools — currently `alwaysAsk` is a core-tool capability, not settable by MCP servers; **UNVERIFIED** whether any config can force per-server always-ask today beyond project `ask` rules — project rules can do `ask` per toolName pattern, which is the available mechanism).
- Never trust names: the official-CUA precedent (§3.2) is the rule PaySwap must follow for any "trusted PaySwap provider" capability — capability keys must be host-verified, never name-wildcards.
- "Always allow" for app-tools is session-only by design; PaySwap must not build flows that assume persistent auto-approval of money-moving app tools.

### 4.5 Inherited product rules

- `AGENTS.md`: no secrets in logs/examples/commits; state owners must be single; spec-first changes; `pnpm typecheck`/`lint`/`architecture:check` gates.
- `apps/zcode-cli/AGENTS.md`: every tool declares `inputSchema`, side-effect scope, permissions; "external extensions such as MCP, plugins, and subagents must be integrated through capability declarations, schema validation, namespace isolation, and permission gatekeeping, and must not directly obtain internal module implementation capabilities"; external I/O must converge to adapters (network via unified entry for "timeouts, retries, backoff, authentication, proxies, custom certificates, rate limiting, logging, auditing"); traceId propagation mandatory.

## 5. Where a financial provider plugin would plug in

**The blessed path (all symbols verified):**

1. **Ship a plugin** with `.zcode-plugin/plugin.json` declaring:
   - `mcpServers`: a `stdio` server (`command: "node", args: ["${ZCODE_PLUGIN_ROOT}/dist/server.mjs"]`) — exactly the pattern in `UI_PLUGIN.en.md` §"Adding a UI to Your Plugin", and identical in shape to existing first-party plugins (see `apps/zcode-cli/packages/*-plugin/`, e.g. `ios-simulator-plugin`, `pdf-plugin`). The resolver gives it the namespaced name `plugin:<name>:<server>`; model-visible tools become `mcp__plugin_<name>_<server>__<tool>`.
   - `userConfig` for non-secret configuration only (account id, base URL, mode); **secrets** should go through a credential service integration, not `userConfig` (§4.1).
   - optional `ui.surfaces[]` for a PaySwap dashboard panel (Side Pane) with `resourceUri: "ui://payswap-stripe/…"` and `availability: "session"`; tools carry `_meta.ui.resourceUri`/`_meta.ui.surface`/`_meta.ui.visibility` for inline cards.
   - optional `skills/` (provider playbooks), `agents/` (e.g. a payments-ops subagent with `permissionMode` restrict-only), `commands/`.
2. **Distribution**: builtin/CDN via the official marketplace (`zcode-plugins-official`, sha256-verified zips — the only channel with package integrity), or personal sources (git/URL/directory — user-added trust). Install path for the PaySwap product: seed as builtin plugins in `apps/zcode-cli/packages/<provider>-plugin/` registered via `OFFICIAL_PLUGIN_DEFINITIONS` / `DEFAULT_ENABLED_OFFICIAL_PLUGIN_IDS` (`apps/zcode-cli/packages/bootstrap/src/app/official-plugin-definitions.ts`), which is how existing official plugins ship.
3. **Server process**: a Node MCP server (SDK pinned per `UI_PLUGIN.en.md`: `@modelcontextprotocol/sdk` 1.29.0 for servers) that holds provider credentials injected via env, performs all Stripe/PayPal/Paystack network calls (pages never do), writes persistent state under `${ZCODE_PLUGIN_DATA}` (→ `<storageRoot>/data/<sanitized-plugin-id>`), and registers `ui://` HTML resources.
4. **UI**: pages use `@modelcontextprotocol/ext-apps` `App` (or the in-sandbox `window.zcode` legacy alias), `app.callServerTool()`, `updateModelContext()`, `createSamplingMessage()`, `registerTool()` for page tools (model-visible as `app__<server>__<tool>`). Panels mount through the Side Pane surface feed (`packages/ui/src/plugin-ui/PluginUiSidePane.tsx`, `pluginUiSurfaceStore.ts`, `pluginUiSurfaceFeedStore.ts`).
5. **Host-side additions (if any)** must go through managed modules: register via `pnpm architecture:adopt`, provide `contract.ts`/`CONTRACT.md`, public entrypoints only, layer order `contract < domain < app < adapters < ui` (`.agents/skills/architecture-governance/SKILL.md`; `architecture-policy.yaml` globals `managedOnly: true`, `forbidCycles: true`, `forbidDeepImports: true`, `maxFileLines: 800`, rule `unmanaged-new-file`).

**What CANNOT be done (architecture violations, cited):**
- **No direct `window.zcode` calls from app UI**: "components access services via `packages/ui/src/hooks/`; platform operations go through `IPlatformService` (`packages/shared/src/platform.ts`), not direct calls to `window.zcode`" (`AGENTS.md` "UI and platform boundaries"). The preload bridge (`packages/desktop/src/preload/index.ts:265` `contextBridge.exposeInMainWorld("zcode", …)`) is Desktop-only platform plumbing behind that interface.
- **No UI→Repo references, no Service→Runtime-implementation references, no cross-domain imports, no cycles**: "UI is forbidden from calling Repo directly, Service referencing Runtime concrete implementations, cross-domain imports of implementation details, and circular dependencies" (`AGENTS.md` "Implementation and verification"); enforced architecturally by `architecture-policy.yaml` (public entrypoints per module, layer direction, `unmanaged-new-file` for new files under `packages/`/`apps/`).
- **No parallel runtime/second process model for providers**: providers ride the plugin/MCP surfaces; AGENTS.md/CLI-AGENTS mandate that MCP/plugin/subagent extensions enter "through capability declarations, schema validation, namespace isolation, and permission gatekeeping", and external I/O converges to adapters rather than bespoke fetch/http sprinkled in business modules (`apps/zcode-cli/AGENTS.md` "External I/O boundary convergence").
- **No business state in Main** and **no plugin storage reads from Main**: `pluginSandbox/CONTRACT.md` "this module does not access plugin SQLite or business files"; Main is forwarding/registry only.
- **No project-config plugin injection**: workspace `.zcode/config.json` cannot add `plugins.dirs` (stripped in `normalizeProjectConfig` — "project configuration must not introduce plugin root directories") and project hooks are trust-gated; a cloned repo cannot auto-enable PaySwap plugin code. Provider plugins must therefore be user/official-installed, never repo-carried.
- **No remote/web UI-plugin surfaces yet**: interactive pages are local-workspace Desktop only ("Interactive pages currently run in local workspaces in ZCode Desktop. Web, mobile, and remote workspaces retain ordinary MCP tool records" — `UI_PLUGIN.en.md`, consistent with `plugin-ui-bridge/CONTRACT.md` "only local workspace Agent is supported").

## 6. Risks and gaps (financial-use lens)

1. **Plaintext plugin secrets (HIGH).** `userConfig` options — including `sensitive: true` values — persist as plaintext JSON (`updatePluginOptionsInFileConfig` → `<workspace>/.zcode/config.json` or user config; `sensitive` only gates template expansion, §4.1). Workspace scope additionally means secrets can be committed to repos by accident. **Action for PaySwap:** provider API keys must use a credential store (extend `ICredentialService` per provider/account), and the `sensitive` flag must never be treated as storage encryption.
2. **Credential encryption is obfuscation by default (HIGH).** `credentialCipherProvider` falls back to a deterministic key derived from platform/homedir/username (`providers/credentialCipherProvider.ts:24-38`); safeStorage migration is a comment, not code. Any local malware with user privileges reads provider secrets. **Action:** prioritize the safeStorage-backed cipher before storing Stripe/PayPal/Paystack keys.
3. **Third-party plugin hooks execute shell commands without a trust gate (HIGH for a finance workstation).** `canRunPluginHooks` returns `true` for all plugins (§1.5) — the source itself flags the abandoned boundary and names the upgrade path ("when per-plugin trust is needed (e.g. a user-config whitelist), pull the check back here"). Installing any third-party plugin currently grants hook-time shell execution with plugin env overlay. PaySwap should (a) treat plugin install as a high-consequence action in product UX, and (b) upstream the per-plugin trust gate before allowing third-party plugins near financial workspaces.
4. **MCP annotations are self-asserted (MEDIUM).** `readOnlyHint`/`destructiveHint` come from the (potentially untrusted) server; a lying server downgrades its risk presentation (though `needsApproval` stays `true` and default risk for unknown tools is `medium`). PaySwap provider tools should declare `destructiveHint: true` for money movement; PaySwap's own UI should not infer safety from hints alone.
5. **Yolo-mode precedence nuance (MEDIUM).** In `PermissionService.checkPermission`, the `mode.yolo` allow fires **before** the service-level `disallowedTools` deny for non-`alwaysAsk` tools (order verified; the code's own comment acknowledges "yolo currently allows before disallowedTools"). Mitigations that exist: `registerMcpTools` filters allowed/disallowed tool lists at registration, and `alwaysAsk` tools hard-check first — but a provider cannot set `alwaysAsk` from MCP metadata. **Action:** if PaySwap must guarantee that money-moving tools can never run under yolo, that guarantee needs an upstream mechanism (e.g. per-server hard-deny or alwaysAsk-equivalent for MCP tools), not just a `disallowedTools` entry.
6. **No OS-level sandbox for MCP stdio servers (MEDIUM).** Provider server processes run with user privileges; the isolation tooling is env hygiene (`sanitizeZCodeRuntimeEnv`) plus permission gating at the tool layer. There is no seccomp/container for MCP servers (the CLI's sandbox story for Bash tools was not audited here — **UNVERIFIED** for Bash-side sandboxing). Financial providers handling raw card data should keep PANs out of the local process entirely (tokenized APIs only).
7. **Result-size and timeout ceilings (LOW/product constraint).** MCP tool results: 100 KiB inline / 50 KiB model text (official CUA excepted), default 30 s timeout (`createMcpToolEntry`); app tools have claim+call deadlines (`MCP_APPS_APP_TOOL_CALL_TIMEOUT_MS` et al.). Transaction listings/refund batches must paginate or use artifacts (`strategy: "artifact"` exists for `node_repl` results; the MCP path is `truncate` — design provider tools to return summaries + references, per CLI-AGENTS "large-volume tool results should not be fed directly back into model context").
8. **Store/`window.zcode` legacy aliasing (LOW, confusion risk).** Two distinct `window.zcode` surfaces exist: the main preload bridge (Desktop platform ops; forbidden for direct UI use) and the sandbox page compatibility alias (renderer-injected, page-only). Audit any PaySwap code touching either to ensure the correct one; the legacy alias lacks sampling/page-tool helpers (`UI_PLUGIN.en.md`).
9. **Under-documented surfaces.** `packages/services/src/runtime-tools/` and `packages/services/src/mcp-sync/` (host-side MCP status/sync surfaces) were only skimmed — **UNVERIFIED** beyond their existence; if PaySwap needs a "provider status" page beyond plugin UI surfaces, audit these before use. `docs/design/v2/tool/00-tool-change-chain.md` (referenced by `apps/zcode-cli/AGENTS.md` as mandatory reading before any tool change) was not read in this pass — PaySwap tool work must start there.
